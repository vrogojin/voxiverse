## 1. Problem + owner-approved scope

Structures exist only as near voxels today. A player's tower vanishes at the 128-block near edge
(`TerrainConfig.near_render_radius()`, terrain_config.gd:171-176) and is invisible from flight/orbit;
there are no generated settlements at all. Owner decisions (full scope, built in phases):

(a) **A procedural village/structure GENERATOR** populates the world deterministically (TreeGen-style,
    hash-of-position, bijection-provable so near and far agree by construction).
(b) **The FAR representation is a baked, decimated LOW-RES VOXEL MODEL per structure** — an accurate
    coarse voxel model like the far-tree archetype mesh, NOT a textured box.
(c) **NEAR-HANDOFF CULL** — the far model turns off once the structure's near blocks stream/mesh in,
    via the same predicate task #120 designs for far-trees (shared, not duplicated).

Constraints inherited from the engine: web gl_compatibility at 40 fps, draws are the scarcest
resource (the project fought 204→~6), NEVER-OOM ([[voxiverse-never-oom-web]]: hard byte caps,
40 MB global ceiling cited at cube_sphere.gd:1862), all work flag-gated byte-identical off.

## 2. Codebase ground truth (what the design must reuse)

### 2.1 The edit overlay — the ONLY source of player-built truth

| Fact | Where |
|---|---|
| `_edits: Dictionary` — the sparse edit overlay; value 0 = dug air, >0 = packed placed cell | world_manager.gd:247 |
| Under FACETED the key is the packed `(fid, cell)` int `FacetAtlas.edit_key` — a total bijection with `edit_key_unpack` / `edit_key_fid` | facet_atlas.gd:172-188 |
| `_edits_by_fid` — per-facet index of edit keys, behind `FP_EDIT_FID_INDEX` | world_manager.gd:260, cube_sphere.gd:2603 |
| **`_write_cell` is THE single write choke point** — break/place/collapse/snow-sim all route here; the fid index is maintained at first-write | world_manager.gd:1901, 1931-1942 |
| `sim_revert_cell` is THE only `_edits` erase | world_manager.gd:1968, 1976-1985 |
| `block_id_at` = `CellCodec.mat(cell_value_at(cell))`; `cell_value_at` is edit-overlay-else-generated — THE cell query (CLAUDE.md rule 1) | world_manager.gd:1539, 1432 |
| `place_block` (hotbar) validates then routes to `_write_cell`; `_structural_update` judges collapse | world_manager.gd:1858-1880, 4089 |
| The snowfall sim ALSO writes through `_write_cell` (snow cells are edits) | world_manager.gd:1953-2001 |
| `edit_count()` — the rev the far-trees delta gate already polls | world_manager.gd:611 |

Consequence 1: player-structure detection can be maintained **incrementally at exactly two choke
points** (`_write_cell` / `sim_revert_cell`) and can never miss a mutation, because no other code
path mutates the overlay. Consequence 2: sim-written snow must be **filtered by material** or every
snowfall becomes a "structure".

### 2.2 The deterministic-placement pattern to copy (TreeGen)

`godot/src/world/tree_gen.gd` is the proven template: one candidate per grid cell, integer-hash
gates, jitter bounded so a feature's footprint stays inside its own cell ⇒ `block_at(x,y,z)` is O(1)
(consult only the owning cell's feature). Key parts: `_hash01` integer mix (tree_gen.gd:88-93),
`_base_pos` jitter [2, G−4] keeping canopy r≤2 inside the G=10 cell (tree_gen.gd:98-101), gate salts
11/22 then biome (`has_tree`, tree_gen.gd:130-140), `tree_info` — the additive far-enumeration
query the far-trees tier drives (tree_gen.gd:235-246), `archetype_cells` — the far model source
(tree_gen.gd:270+). Worldgen consults `TreeGen.block_at` inside `resolve_cell`
(terrain_config.gd:1387, 1420, and the smoothing/snow stencils at 1537, 1633, 1725, 1881, 1987, 2008).

**C++ generator reality (the P1 gotcha):** under `FP_CPPGEN` (cube_sphere.gd:224, currently const
false) the near stream is generated by `VoxelGeneratorCosmos` (module_world.gd:4100), and engine
patch `docker/engine/patches/godot_voxel/0007-cosmos-cpp-generator.patch` **fully mirrors TreeGen**
(patch lines 732-780: `tree_base_pos`/`tree_species_for`/`tree_has_tree`, "the slope port drags
TreeGen in with it"). Any new worldgen feature consulted by `resolve_cell` must either be mirrored in
the patch or interlocked so both flags are never live together (§6.4).

**The air-ceiling stencil (the second P1 gotcha):** the streaming fast path bounds each column's
per-cell resolve by a 5×5 neighbourhood max + `max_above` — 5×5 *specifically because* a tree's base
jitter ±2 columns can reach the column (module_world.gd:3692-3707); the worldgen vertical envelope
likewise adds `TreeGen.MAX_ABOVE_SURFACE` (terrain_config.gd:271). A house whose footprint spans 9
columns breaks the 5×5 assumption — §5.4 designs the (cheap, hash-gated) widening.

### 2.3 The far-impostor tier to mirror (FacetFarTrees) — SHIPPED precedent

`godot/src/world/facet_far_trees.gd` is the exact architectural shape to clone:

- Owned/stepped by the ONE `FacetFarRing`: constructed at facet_far_ring.gd:539-540, re-targeted at
  633-634, stepped (settle-gated, credit-gated) at 1334-1335, sun/chop/edits-rev feeds at 5140-5162.
- Children of the ring node inherit placement transform / anchor shifts / SN3 scaled placement —
  orbit-frame correctness for free (facet_far_trees.gd:13-16).
- Per-facet enumeration OFF-THREAD, one facet per job, LRU-cached, dwell-evicted
  (`_enum_worker` facet_far_trees.gd:546, `_wanted_facets` :603).
- Radial `voxi_shade` sun-weld: `ALBEDO = col · voxi_shade(normalize(world_pos − planet_centre),
  sun_dir)`, seeded from `TierPlace.last_sun_dir()` (FP_FAR_TERMINATOR_WELD; facet_far_trees.gd:27-34).
- **FP_FAR_TREES_DELTA rebuild-on-change gate** ([[voxiverse-forest-fps-root]]): rebuild only when
  (camera moved past threshold, cache epoch bumped, edits rev changed) — facet_far_trees.gd:117-135.
  Structures get the same gate from day one; a per-step full rebuild is the known fps trap.
- `total_bytes()` asserted ≤ a hard `*_BYTES_MAX` (facet_far_trees.gd:1057; the §2.4 tier convention
  of the far-trees doc).

### 2.4 The decimator precedent (FacetBlockLod)

`godot/src/world/facet_block_lod.gd` is the shipped 2× downscale: MIN top / MAJORITY id (vote among
children within one coarse pitch of the top, ties → smallest id — deterministic) / OR water
(`decimate` :91-134, `_majority_id` :140-153). §6 adapts the **majority-colour + deterministic
tie-break law** verbatim, but explicitly NOT the MIN-height rule: MIN is a *terrain containment* law
(no-protrusion); applied to a structure it erases 1-block walls and roofs entirely. Structures need
**OR-occupancy** (§6.1) — the opposite trade, justified there.

### 2.5 The worker lane + slot conventions

`JobLane` (job_lane.gd:8-24): dispatch = pure CPU on a WorkerThreadPool slot, commit = main-thread
GPU touch under a budget; priorities at :33-39; `submit` at :85. Bakes run at
`PRIORITY_OPPORTUNISTIC` (a far cosmetic), rebuild commits are one mesh swap. No new threads —
the Emscripten pool is fixed ([[voxiverse-web-core-count]]).

### 2.6 The near-presence probes that exist today (and their trap)

`module_world.skin_near_meshed(fid, aabb)` (module_world.gd:2536) routes to godot_voxel
`is_area_meshed`, "true only when EVERY mesh block in the box is applied" (facet_skin_tier.gd:82,
275). **The dead-latch class** ([[voxiverse-grassbase-backstop]], #113/#89): a probe box that can
never fit inside the terrain's bounds slab (or the near radius) returns false forever — the
applied-cover ladder was dead for months because its y±128 probe never fit the [−64,130] slab. The
shared predicate (§7.3) bakes the slab-clamp + reachability into ONE place so neither trees nor
structures can re-create the latch.

## 3. Architecture overview

```
                      ┌────────────────────────────────────────────┐
   _write_cell /      │            StructureRegistry               │   enumerate_facet(fid)
   sim_revert_cell ──►│  id → {source, fid, bbox, rev, mats, ...}  │◄── StructureGen (P1, hashes)
   (player clusters)  │  ONE table, TWO producers                  │    derived on demand, never global
                      └───────────────┬────────────────────────────┘
                                      │ dirty/rev
                              ┌───────▼────────┐        JobLane worker (dispatch)
                              │ StructDecimator│──────► coarse cell set + colours
                              └───────┬────────┘        (reads block_id_at ⇒ damage shows far)
                                      │ baked model
                              ┌───────▼────────────┐    main-thread commit (mesh swap)
                              │ FacetFarStructures │──► 2 draws (LOD-A + LOD-B merged meshes)
                              │ (child of FarRing) │    radial voxi_shade, sun-weld, delta gate
                              └───────┬────────────┘
                                      │ hide when
                              ┌───────▼────────┐
                              │  NearPresence  │◄──── shared with FacetFarTrees (task #120)
                              └────────────────┘
```

Design laws:

1. **One registry, two producers.** Player clusters (P0) and generated villages (P1) are the same
   record shape; everything downstream (bake, far render, handoff cull, ledger) is source-agnostic.
2. **Generated structures are worldgen, not edits.** `StructureGen.block_at` is consulted beside
   `TreeGen.block_at` in `resolve_cell` (§5.3) so NEAR rendering, analytic physics, collapse, and
   the far bake all read the same cells through `block_id_at` with zero new machinery — CLAUDE.md
   rule 1 kept intact. (The rejected alternative — stamping generated blocks through the edit
   overlay — corrupts "edits = player", the fid index, save semantics, and the P0 clustering; see §5.6.)
3. **The far model reads THE cell query.** The decimator samples `block_id_at` over the bbox, so a
   player-damaged village house is coarse-damaged at distance automatically (edits override
   generated in `cell_value_at`, world_manager.gd:1432).
4. **Far tier mirrors FacetFarTrees** in ownership, stepping, lighting, suspend, delta gate, ledger.

## 4. Part A — player-built structure identification (P0)

### 4.1 What counts

A **player structure** = a 6-connected component of *placed* overlay cells (packed value > 0,
material not sim-managed) with `count ≥ STRUCT_MIN_BLOCKS := 16` and bbox extent ≥ 3 on at least two
axes (filters pillars/floors of tossed blocks; both consts beside the flag, tunable).

Excluded from clustering: dug-to-air entries (value 0 — they shape terrain, they aren't built
volume), and **snow-family materials** — the snowfall sim writes real overlay snow cells through the
same choke point (world_manager.gd:1953-2001); without the material filter a blizzard becomes a
"structure". Filter = `BlockCatalog` snow ids (data-driven, one const set).

### 4.2 Incremental connected components (bounded, never-OOM)

New `godot/src/world/structure_tracker.gd` (`class_name StructureTracker extends RefCounted`),
owned by WorldManager, driven from the two choke points:

- **State**: `parent: Dictionary` (edit_key:int → edit_key:int) union-find over qualifying placed
  cells; `clusters: Dictionary` (root → {count, bbox_min, bbox_max, mats histogram(≤8), rev}).
  Keys are the existing `FacetAtlas.edit_key` ints — no new coordinate scheme; `edit_key_unpack`
  (facet_atlas.gd:177-184) recovers `(fid, cell)`; neighbours are `edit_key(fid, cell±axis)`
  (same-facet only, see §4.4).
- **On place** (hook: tail of `_write_cell`, world_manager.gd:1901, behind `FP_STRUCT_DETECT`, after
  the fid-index block at :1931-1942 — same first-write discipline): if the material qualifies,
  make-set, then union with each of the ≤6 face-adjacent placed cells' sets. Amortised O(α(n)) per
  edit; path-halving keeps it iterative (no recursion — web stack).
- **On remove** (hooks: `_write_cell` when overwriting a tracked cell with air/non-qualifying, and
  `sim_revert_cell`, world_manager.gd:1968): removal can SPLIT a component — exact incremental
  decremental connectivity is not worth its complexity here. Law: decrement count/histogram, mark
  the owning cluster **DIRTY**; a debounced (≥1 s) paced job re-flood-fills only that cluster's
  cell set (worker-side over a snapshot array of its keys — bounded by the cluster's own size) and
  re-registers the resulting components. Until it runs, the stale bbox only *over*-covers (the far
  model may linger one beat too large — cosmetically safe, never a hole in the world).
- **Registry sync**: a cluster crossing the threshold registers; dropping below unregisters; every
  mutation bumps its `rev` (the bake/rebuild delta signal, §7.2).

### 4.3 Bounds (NEVER-OOM)

`parent`/`clusters` are O(tracked placed cells) — the same order as `_edits` itself, which gameplay
already bounds. Hard cap `STRUCT_TRACK_MAX := 65536` tracked cells; at the cap new placements are
counted but not clustered (telemetry flag `tracker_saturated`, log-once) — degrade, never grow.
Registry cap `STRUCT_REG_MAX := 256` (largest-first retention). Ledger: `StructureTracker.total_bytes()`
= dict-entry arithmetic, asserted in the gate (§10).

### 4.4 Known v1 limitations (accepted, documented)

- A build spanning a facet seam clusters per-fid (edit keys are fid-scoped) → two structures, two
  far models meeting at the seam. Acceptable v1; a cross-fid merge pass is P2 polish.
- Blocks placed *on* a generated village house extend the player cluster, not the village record —
  both models bake from `block_id_at` so the visuals compose; double-cover inside one bbox
  overlap is bounded and resolved by the handoff cull anyway.

## 5. Part B — the procedural village generator (P1, `FP_STRUCT_GEN`)

### 5.1 Placement law (the TreeGen bijection, one level up)

New `godot/src/world/structure_gen.gd` (`class_name StructureGen`), all static, hash-of-position,
**no state** — mirroring tree_gen.gd's structure exactly. Salts must be disjoint from TreeGen's
{11,22,33,44,55,66,88,121-125} — StructureGen uses the 200-range.

```
V := 192                                  # village lattice pitch (columns); ~2-4 candidate cells/facet
H := 32                                   # house sub-lattice pitch inside a village
VILLAGE_CHANCE := 0.05                    # salt 201 gate on the (vx, vz) village cell
HOUSE_CHANCE   := 0.55                    # salt 202 gate per (hx, hz) sub-cell inside a live village
FOOT_MAX := 11                            # house footprint ≤ 11×11; jitter ∈ [2, H−FOOT_MAX−2]
                                          #   keeps the WHOLE footprint inside its own H-cell
STRUCT_MAX_ABOVE_SURFACE := 12            # walls 3-4 + roof ≤ 12 blocks over base (envelope term)
FOUNDATION_MAX := 4                       # fill below base at most 4 blocks (slope skirt)
```

`has_village(vx, vz, pcache)` gates: hash 201, then **body gate first** — Earth facets only,
*before* any biome consult (the Moon reuses biome ids 11/12/13; the exact alias trap of
[[voxiverse-tree-bugs-rootcause]] and far-trees §5.5) — then site test: anchor column
`biome_at ∈ {B_PLAINS}` (+ `B_SAVANNA` only under `FP_CLIMATE_BIOMES`, reusing the flag exactly as
`_species_for` does, tree_gen.gd:105-125), `height_at` 4×4 stencil at pitch 8 with `max−min ≤ 4`
(flat-site), anchor `> SEA_LEVEL + 2`. `house_info(hx, hz, pcache)` gates: owning village live,
hash 202, then per-house local flatness (footprint corners `max−min ≤ 3`, else that house is
skipped — terraces stay honest); emits `{base: Vector3i, w, d, wall_h, roof, mats}` — every
parameter a salt-203..209 hash. Heights via `TerrainConfig.column_top` (terrain_config.gd:1667,
the worker-safe fid-scoped sampler far-trees already uses).

**O(1) `block_at` by construction:** the jitter bound keeps a house's footprint inside its own
H-cell, so `StructureGen.block_at(x, y, z, pcache)` consults only (x,z)'s own sub-cell's candidate
house — the identical trick to `_base_pos`'s canopy bound (tree_gen.gd:98-101). Early-outs: village
patch hash first (1 hash kills ~95 % of columns), then house hash, then the footprint test. Cost on
the resolve hot path ≈ 1-3 integer hashes per column — the same class as the tree gate, web-safe.

### 5.2 House template (v1 minimal, data-driven)

A house is a parametric box: foundation fill (cobble) from `base.y−FOUNDATION_MAX`..base, floor,
`wall_h` wall courses (plank walls, log corner posts), a door gap on the hash-chosen side, one
window gap per long wall, flat or gabled roof (plank/log). Interior = air (enterable). Materials
come from `BlockCatalog` ids only — adding a house style is a data change (CLAUDE.md's "adding a
material is a data change" spirit). Paths/wells/farms are explicitly **P2 decorations**, not v1.

### 5.3 NEAR integration — real blocks, one sampler

`StructureGen.block_at` is consulted **beside `TreeGen.block_at`** at the `resolve_cell`
consultation sites (terrain_config.gd:1387, 1420; precedence: edits > structure > tree > terrain —
a house clears any tree cell inside its footprint by winning the consult order, and `has_village`'s
site gate keeps bases apart in practice). Because `block_id_at → cell_value_at` falls through to
the same generated path (world_manager.gd:1432-1539), **analytic physics, floor_under, the DDA
raycast, GroundCollider, and `_collapse_unsupported` all see the house with zero new code** —
breaking a wall detaches the roof exactly like chopping a trunk detaches a canopy. This is the
whole payoff of rule 1 and the reason Option A (worldgen) beats Option B (overlay stamping, §5.6).

### 5.4 The two streaming-fast-path touches — **SUPERSEDED by §12.2** (the height-budget law
dissolves the col_hi widening entirely; kept for the record)

1. **Vertical envelope** (terrain_config.gd:271): `max_above` becomes
   `max(TreeGen.MAX_ABOVE_SURFACE, SNOW_FILL_MAX_CELLS, StructureGen.STRUCT_MAX_ABOVE_SURFACE)`
   under the flag (12 vs 14 — the tree term already dominates; likely a no-op, assert it in the gate).
2. **Air-ceiling stencil** (module_world.gd:3692-3707): the 5×5 max-g stencil cannot see a house
   whose base is up to `FOOT_MAX/2 ≈ 5` columns away. Widening to 11×11 for every column is the
   wrong trade; instead the col_hi computation adds a **hash-gated term**: if (x,z)'s H-cell house
   gate passes (≈2 hashes; the village patch hash kills almost all columns first), raise `col_hi` by
   the house's `wall_h + roof + FOUNDATION` over its base. Exact, O(1), and zero cost where no
   village exists. Mirrored in the C++ generator when that lands (§6.4… see below).

### 5.5 Registration into the registry

The far tier never scans the world: `StructureGen.enumerate_facet(fid, pcache)` walks the ≤ ~9
V-cells overlapping the facet (417-block edge / 192 pitch), then live villages' H-cells → ≤ ~36
house tests/facet — trivially cheaper than the far-trees 1 739-cell scan (facet_far_trees.gd:546).
Runs on the same worker/LRU/dwell machinery; GEN records carry `{fid, bbox, house params hash}` so
the decimator can bake **without** the registry ever holding blocks. Deterministic ⇒ the registry's
GEN half is a pure cache, evictable at will (never-OOM by construction).

### 5.6 Rejected alternative (recorded)

**Overlay stamping** — generator writes houses through `_write_cell` on first visit. Rejected:
pollutes "edits = player" (P0 clustering would classify villages as player builds), bloats `_edits`
and the fid index with thousands of keys per village (the R4/R5 crossing-cost class,
world_manager.gd:254-262), breaks determinism-from-hash (stamped state must be persisted/remirrored,
`_remirror_module_edits` world_manager.gd:3754), and still needs the streaming repaint. Worldgen
integration costs one consult site + two fast-path touches and gets physics/collapse/streaming free.

## 6. Part C — the decimated far-model bake (`StructDecimator`)

### 6.1 Decimation law (adapted from FacetBlockLod, deliberately inverted)

Input: the structure bbox; sampler = `WorldManager.block_id_at` (P0 player builds AND damaged
villages) or pure `StructureGen.block_at` + terrain (worker-side pristine GEN bake — no WorldManager
access on workers; a damaged village re-bakes main-thread-sampled, §7.2). Output per LOD: a coarse
occupancy grid + one colour byte per solid coarse cell.

- **Coarse pitch**: `c = max(1, 2^ceil(log2(max_extent / TARGET_RES)))`, `TARGET_RES := 16` —
  a 5×7×4 house bakes at c=1 (it IS its own model, ≤ 200 cells), a 40-block castle at c=4,
  a 200-block mega-build at c=16. LOD-A uses `c`, LOD-B uses `c×2` (P2).
- **Occupancy = OR of the c³ children** (any solid child ⇒ coarse solid). This is the deliberate
  inversion of FacetBlockLod's MIN rule (facet_block_lod.gd:20-24): MIN exists for *terrain
  no-protrusion containment*; on a structure it deletes 1-block walls, roofs, and pillars — i.e.
  exactly the recognisable silhouette. OR dilates by ≤ one coarse cell — for an *impostor that is
  culled before the player gets near* (§7.3), silhouette fidelity outranks containment, and the
  far-over-near protrusion law is enforced by the handoff cull + band gate, not by the model shape.
- **Colour = MAJORITY block id among the solid children**, ties → smallest id — the
  `_majority_id` law verbatim (facet_block_lod.gd:140-153); colour via `BlockCatalog.color_of`
  routed through the far colour law ([[voxiverse-far-skin-block-color]]) so far models match the
  skin and near blocks by construction.
- Deterministic: same inputs ⇒ byte-identical model (gate G-ST-DECIM re-derives and compares).

### 6.2 Mesh representation

Per structure per LOD: greedy face-merge the coarse cell set (the FacetBlockLod §4 discipline:
merged top/side quads across equal-colour runs) → a local-space vertex/colour array. These are
**unique geometries** — MultiMesh (one mesh, many instances) is the wrong tool; instead
`FacetFarStructures` merges all *wanted* models into **ONE ArrayMesh per LOD band** (2 draws
total), verts pre-placed in ring-local coords via `FacetAtlas.lattice_to_world64`
(facet_atlas.gd:402) + the far-trees sink law (base = min-corner `column_top` − BURY 1.0,
far-trees §4.3 — models stand on the tier datum, never float).

### 6.3 Where the bake runs

JobLane (`job_lane.gd:85 submit`, `PRIORITY_OPPORTUNISTIC` :39): dispatch decimates + greedy-merges
into caller-owned arrays (pure CPU, the far-ring worker contract), commit swaps the ArrayMesh
(one bounded GPU touch). Per-structure bake ≈ bbox volume scan ≤ 64³ worst = 260 k samples — chunk
the dispatch (the JobLane CHUNKED convention) so one mega-build never owns a worker slot for
hundreds of ms on 2-core web ([[voxiverse-gen-class-costs]] ×25). Rate: structures change rarely;
the delta gate (§7.2) makes rebakes event-driven, not periodic.

### 6.4 The C++ mirror interlock (P1 reality) — **SUPERSEDED by §12.1/§12.6** (FP_CPPGEN is TRUE in
the served pck, and the mirror ships as a new cumulative patch 0013, not an edit to 0007)

`FP_CPPGEN` is const false today (cube_sphere.gd:224) — P1 ships GDScript-only and is honest.
The interlock: `verify_structures` asserts `not (FP_STRUCT_GEN and FP_CPPGEN)` until **P1b** adds
the StructureGen mirror to patch 0007 beside the tree port (patch lines 732-780) + the §5.4(2)
col_hi term, gated by a `gen.set("fp_struct", …)` parameter (the `fp_stamp` precedent,
module_world.gd:4077). P1b is an engine rebuild (~24 min cold) — schedule it with the next planned
rebuild, not alone. The byte-equality gate pattern from the original FP_CPPGEN port applies.

## 7. Part D — the far render tier + near-handoff cull

### 7.1 `FacetFarStructures` (new file, clone of the FacetFarTrees shape)

`godot/src/world/facet_far_structures.gd` (`class_name FacetFarStructures extends RefCounted`):

  `voxi_shade(normalize(world_pos − planet_centre), sun_dir)` with `planet_centre` as a uniform

### 7.3 THE SHARED HANDOFF PREDICATE (coordinate with task #120)

New tiny static helper `godot/src/world/near_presence.gd` (`class_name NearPresence`) — the ONE
"near blocks are meshed here ⇒ hide the far impostor" law, consumed by FacetFarStructures AND
FacetFarTrees. **Owned by task #120** (implements first; COSMOS-FARTREE-ALIGN-DESIGN.md §5.1/§5.6
is the implementing spec — this section matches it). Contract agreed 2026-08-12:

```
NearPresence.covered(world: WorldManager, fid: int, box: AABB) -> int
    # returns COVERED / NOT_COVERED / UNKNOWABLE — PURE READ, never touches streaming state
    a. clamp box.y to the terrain bounds slab (the FP_APPLIED_PROBE_SLAB lesson — an unclamped
       probe is the #89/#113 dead-latch class); clamp empties the box → NOT_COVERED definitively
       (near can NEVER mesh it, the far model must show — the safe, useful answer)
    b. probe module_world is_area_meshed (the skin_near_meshed shape, module_world.gd:2536,
       2044-2050); TRUE → COVERED unconditionally — a positive mesh probe is a fact at ANY distance
    c. FALSE + box not FULLY inside the live near reach (viewer_view_distance / pool view,
       module_world.gd:505, 2576 — read live, never hardcode 128) → UNKNOWABLE;
       FALSE + fully inside reach → NOT_COVERED
    d. no module / no is_area_meshed (GDScript render path) → UNKNOWABLE, explicit and gate-asserted
```

**Evaluation order is COVERED-first, load-bearing (#120 finding):** a radius-gate-first variant
(probe only inside the live reach) silently un-fixes #120 — the double-render band lives precisely
in the 32-block chunk-quantisation shell [reach, reach+32] (mesh_block_size 32,
module_world.gd:393), whose columns CAN be meshed. Only the NEGATIVE answer is radius-ambiguous;
gating the positive on radius makes that shell permanently UNKNOWABLE exactly where the bug is.

Shared invariant (the only cross-consumer law): **UNKNOWABLE never changes state** — never latch on
an unanswerable probe. Streak values are per-consumer POLICY: trees hide at streak 1 (#120's
requirement is verbatim "the moment the near tree renders, turn off the far one"; a spurious
COVERED cannot occur, so the flicker risk is negative-side only, covered by their SHOW_STREAK=2);
structures use `HIDE_STREAK := 2` / `SHOW_STREAK := 2` (bbox probes flip later than a 1-column
trunk probe; one confirming step costs 250 ms on a model that was already invisible-behind-near).
Trees probe a 1-column box at the trunk base; structures probe their footprint bbox — same
function, different box. Both tiers fingerprint the answer into their rebuild-delta gates (the
FP_FAR_TREES_DELTA re-arm), which is why the pure-read guarantee above is part of the contract.
One gate family `G-NP-*` shared, including the positive-reachability assert (§2.6).

Protrusion posture: inside R0 the near view owns the world (#110/#113 law) — the far model is
culled by the predicate (or the band gate as a floor), so OR-dilated models can never ride over
streamed-in near blocks.

### 12.2 THE HEIGHT-BUDGET LAW — the air-ceiling trap dissolves by constraint (supersedes §5.4)

§5.4(2) planned a hash-gated `col_hi` widening in the streaming fast path. As-built analysis shows
**no fast-path code needs to change at all** if the house geometry is bounded correctly:

- GDScript fast path: `col_hi = mini(cb_top, maxi(gmax + max_above, sea) + 1)`
  (module_world.gd:3704) where `gmax` is the max ground over the column's own 5×5 stencil
  **including its own g**, and `max_above = max(TreeGen.MAX_ABOVE_SURFACE=14, SNOW_FILL_MAX_CELLS=4)
  = 14` (module_world.gd:3441, tree_gen.gd:33).
- C++ path (live): the whole-block early-out `top = max_h + max_above` (patch 0007 hunk lines
  2015-2021), `max_h` = max ground over the block's own columns.

**The law**: every structure cell above a column must lie ≤ 14 blocks above that column's OWN
ground. Derivation: the flat-site gate bounds `base ≤ (any footprint column's g) + STRUCT_FLAT_TOL`,
so house top `≤ g + STRUCT_FLAT_TOL + STRUCT_H_MAX`. Pick

```
STRUCT_H_MAX   := 11     # wall_h ≤ 4 + roof ≤ 7 above base (gable capped to fit)
STRUCT_FLAT_TOL := 3     # footprint-corner max−min gate (§12.4)
⇒ 11 + 3 = 14 ≤ TreeGen.MAX_ABOVE_SURFACE (14)      — GATE-ASSERTED (G-SG-ENV)
```

Since walls/roof/interior/foundation all lie over the footprint, every mesh block containing house
cells contains footprint columns, so the C++ per-block `max_h` bound holds by the same arithmetic;
foundation cells (`base−FOUNDATION_MAX..base`) sit at `y ≤ g + 3` — trivially inside. The vertical
worldgen envelope (terrain_config.gd:271) is likewise already wide enough — asserted, not touched.
**Zero hot-path cost, zero stencil code, mirrored automatically.**

**One real envelope defect found while verifying (pre-existing, independent of structures):**
patch 0007's `generate_block` still uses `max_above = MAX(10, SNOW_FILL_MAX_CELLS)` with the
comment `// TreeGen.MAX_ABOVE_SURFACE=10` (0007 hunk line 1985) — GDScript raised 10→14 for the
jungle tree (tree_gen.gd:29-33) and patch 0011 mirrored 14 only for the tile-bake
(`TREE_MAX_ABOVE_SURFACE = 14`, 0011 hunk line 374), NOT for the near-gen early-out. With
FP_CPPGEN + FP_CLIMATE_BIOMES both live, a jungle canopy crossing a mesh-block boundary in the band
`(max_h+10, max_h+12]` can be clipped by the C++ whole-block early-out while GDScript places
leaves — a latent, rare byte-divergence. **Patch 0013 fixes the literal to the shared 14** (also
what structures need), healing it as a side effect. G-SG-CPP covers it.

### 12.3 `claim_at` semantics — interior air is AUTHORITATIVE (sharpens §5.3)

`StructureGen.claim_at(x, y, z, pcache) -> int` returns **−1** (no claim — fall through to the
existing chain), **0** (interior/door air, authoritative), or **>0** (a house block id). The
tri-state is what makes roof interiors work: a plain "return AIR" would let the snow stack
(`_snow_stack`, consulted at terrain_config.gd:1414-1416) fill cold-column interiors and let
smoothing lips (`_surface_cap` at :1404-1411) grow into doorways. Claim-first suppresses both.

Exactly TWO consult sites, both in `resolve_cell`, mirroring the tree consults:

1. terrain_config.gd:1384-1387 (the `y >= hi` carve branch): claim test before `_sea_block` /
   `TreeGen.block_at`.
2. terrain_config.gd:1394+ (the `y > g` branch): claim test at the TOP of the branch — before the
   g+1 cap, the snow stack, the sea fill and the tree consult.

Precedence: **edits > structure claim > cap/snow/sea/tree** (edits win upstream in `cell_value_at`,
world_manager.gd:1432 — unchanged). Structures never claim `y ≤ g` — the below-ground stackup
(strata/ore/deepslate) stays byte-untouched. Cost on the hot path: a y-window early-out
(`y − g ∉ [−FOUNDATION_MAX, STRUCT_H_MAX]` → −1 with ZERO hashes), then the village-patch hash
kills ~95 % of surviving columns — the same class as the tree gate.

Accepted v1 residuals (documented, cosmetic): (a) the six neighbour-column smoothing/snow stencils
that keep tree columns' tops full (terrain_config.gd:1537, 1633, 1725, 1885, 1955, 1991, 2012) are
NOT taught about houses — a smoothing lip may grow against an exterior wall face; (b) snow never
accumulates ON roofs (the fill baseline `p ≤ g+5` is below every roof top); (c) slope-carve
interplay is avoided by the site gate (§12.4) rejecting sloped footprints — asserted at enumeration
time via `slope_run_of`, never on the hot path.
