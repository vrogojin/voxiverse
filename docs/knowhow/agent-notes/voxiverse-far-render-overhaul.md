**THREAD-COUNT ROOT CAUSE (2026-08-02, CONFIRMED live via 'cores' telemetry).** The web engine pool is ALREADY 16 (versions.env WEB_PTHREAD_POOL=16, engine patch 0001/0002 → -sPTHREAD_POOL_SIZE=16) — a rebuild would NOT change it. The limiter is the CODE: `_pbm_n = clampi(OS.get_processor_count()-1, 1, 8)`, and on web OS.get_processor_count() == emscripten_num_logical_cores() == navigator.hardwareConcurrency, which THE USER'S BROWSER REPORTS AS 2 (live telemetry cores=2). So only 1 bake worker. Forcing more workers than real cores THRASHES (measured: 2 workers = 0.8 facet/s < 1 clean). ⇒ On a genuinely 2-core host we are at the parallelism ceiling (1 worker + main = 2 threads on 2 cores); the 16-pool can't help. The "engine pthread rebuild" the user asked for is a NO-OP (pool already 16); hardwareConcurrency is a browser/OS value the engine cannot raise. OPEN QUESTION for the user: is their machine REALLY 2-core, or is a VM / cloud-desktop / browser-efficiency-policy under-reporting cores to the tab? If the real count is higher, override the detection to use the pool (clamp higher) — but if it's really 2, nothing to gain. So on a 2-core host the only fill-speed levers are per-column cost (C++ 10× but the lock/fps issue) or fewer columns (texels already 64). Added `cores` telemetry.

**NEAR/FAR COLOUR BUG (2026-08-02, FIXED live).** User: far skin water/sand/grass colours differed from the near blocky field. ROOT CAUSE: the flat band + whole-planet fine bake stored `FarPalette.far_color_index_of_block(SurfaceShot.top_block_id(...))` where top_block_id = `detail_pattern(top_col)+1` (a DETAIL-PATTERN id, P_WATER/P_SAND/…), but `far_color_index_of_block` indexes `_block_idx` by BLOCK id — a type confusion. Headless probe: open water #3e76e3 → **mud #614646 (gray)**, sand #dad39f → **stone #909aa4 (gray)**; grass matched only by luck (pat 0 → block 1). So the far tier had been miscolouring most terrain as gray. FIX: `SurfaceShot.top_far_index()` classifies the top COLOUR directly via `FarPalette.far_color_index` (same nearest-frozen rule as facet_tex_baker:1315), and `_pbm_compute` splits edit cells (real block id → far_color_index_of_block, correct) from bare terrain (colour → far_color_index). Prewarmed on main (ensure_far_index_ready) → worker-safe. VERIFIED live: far water now blue, grass green, sand tan, frozen sea → teal ice. LESSON: `surface_shot()["block_id"]` is a DETAIL-PATTERN id (for the textured FP_BLOCK_DETAIL tier), NOT a block id and NOT a flat-colour index — never feed it to far_color_index_of_block.

LESSON: the earlier "whole disc fine at alt 1982" was the BAND (promote 8000, 240 facets) covering the disc, NOT the fine tier — the fine tier was always slow to fill.
