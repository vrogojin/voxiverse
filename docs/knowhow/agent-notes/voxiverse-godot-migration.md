Assessed 2026-07-14 (Fable + 3-agent research → `docs/GODOT-MIGRATION-ASSESSMENT.md`). Decision: **migrate eventually, but NOT now and NOT for visuals.** Target **Godot 4.6.x + godot_voxel 1.6** (newest *paired* stable combo; only hop to 4.7 if Zylann has cut a 4.7-paired voxel release — never pair with voxel master). Effort ~1–2 focused weeks, dominated by re-validation + the emsdk jump + one hard patch rebase.

**Why the user's "migrate for HDR/reflections" thesis is wrong:** the visuals are gated by the **renderer, not the Godot version**. The web export is Compatibility/WebGL2-only on EVERY official Godot through 4.7; HDR/SSR/GI are Forward+/WebGPU features, and WebGPU-on-web is an open proposal with no timeline (only a community 4.6.2 fork exists — unsuitable for our threaded custom-module build). So a version bump buys ~zero browser pixels. The route to great visuals *today* is a **dual-target build**: Forward+ desktop export + Compatibility web (our analytic-physics + decoupled-sim-layer + two-render-path architecture is well-positioned for it). Near-term WebGL2 visual wins achievable on 4.4.1 NOW: custom shaders, SSAO, tonemapping/glow, reflection probes, sky/atmosphere/horizon-fog — see [[voxiverse-gpu-headless-testing]].

**A bump does NOT simplify the [[voxiverse-faceted-planet]] FP-M2 work** — newer godot_voxel (1.5/1.6) adds no blocky-LOD, no rotated multi-terrain, nothing facet-shaped; our Planet Assembly is engine-version-orthogonal. It buys ~1 patch elimination (web pthread-pool native at 4.5/4.6; maybe hw-concurrency clamp → shell JS), 6 patches → ~4. The 4 planet-specific patches (waterlogging, cosmos-bake, facet-carve, hw-clamp) are permanent.

**Top migration risk:** emsdk **3.1.64 → 4.0.11** (major, forced at 4.5) invalidates the NEVER-OOM heap/soak baselines — the Tier A/B GPU-testing harnesses built this session are the re-baselining mitigation. Also: Jolt becomes the default 3D physics at 4.6 (pin it + A/B the mass-tuned block-push/collapse feel); the 21KB waterlogging patch needs a ½-day pre-flight apply-probe; FLAT 6027/0 may legitimately shift across engines (re-pin goldens deliberately).

**Triggers:** T1 = first quiet window after FP-M2 flag-ON soaks live; T2 = standing quarterly watch on official WebGPU-on-web (the day it hits a dev snapshot, the visuals calculus flips → reconsider).

**2026-07-23 UPDATE — T2 tripping; user chose to SPIKE the WebGPU fork.** Live LOD-texture Phase 1 (WebGL2 baked far-satellite texture) landed on main (PR #22, origin/main 3c54198) + F8 snapshot dev-tool (PR #23), but the user tested it live and confirmed the gl_compat CEILING: coarse far surface (16 texels/facet ≈ 26 blocks/texel, only ramps at cam_dist 600-1800, mid-band untextured), plus day-side OVEREXPOSURE (no HDR on R10G10B10A2 tonemapped gl_compat). The user asked for the WebGPU route ("ok if experimental, we could patch on the go"). Research: the community fork matured — **David Walter (godotwebgpu.com, X @davidpwalter), full WebGPU driver on Godot 4.6.2, MIT/open-source, public beta May 2026** (compute shaders, Forward+/Mobile in-browser, cross-browser Chrome113+/Safari18+/Firefox, "zero GPU errors"). This directly challenges the 2026-07-14 "fork unsuitable for our threaded custom-module build" verdict. FEASIBILITY SPIKE (WebGPUSpike agent) findings 2026-07-23:
- **Module compat GREEN (proven):** godot_voxel v1.6 compiled+linked+registered all 70 Voxel classes vs the fork's Godot 4.6.3-rc native editor (8.5min, our EXISTING image, no new toolchain). Corroborated by Zylann's official 4.6+voxel1.6 build. Map: godot_voxel v1.6→4.6, our v1.4.1→4.4.1.
- **Rust libs build+link GREEN (proven):** the 3 WebGPU Rust libs (wgpu_native/naga_native/spirv-webgpu-transform from davnotdev crate forks, pinned in fork's thirdparty/*/TAG; pull davnotdev wgpu branch godot-wgpu-29) build to wasm32-unknown-emscripten (recipe: Rust 1.91.1 + emsdk 4.0.11, feature `fragile-send-sync-non-atomic-wasm`, staticlib-only, panic=abort for clean -fno-exceptions emit, `-fexceptions` is a DEAD END emscripten conflict). LINK into a Godot web template (107MB wasm, 0 undefined symbols). Runtime export built + ready.
- **CRITICAL CATCH (the killer):** on the emscripten target this fork's wgpu-hal has NO WebGPU backend — build.rs gates `Emscripten={target_os=emscripten AND gles}`. So "Godot WebGPU" ON WEB is actually **wgpu-on-WebGL2** (needs wgpu `gles` feature; wasm has WebGL glue + ZERO navigator.gpu/requestAdapter). → NO compute shaders (WebGL2 has none), NO real WebGPU on web. The whole strategic value prop (compute-baked high-res terrain, real WebGPU) is NOT delivered by this fork's web path. A 2-4wk migration would only get a WebGL2-backed RenderingDevice renderer swap (maybe better lighting, no compute) on a moving-target single-maintainer fork (main line already at 4.7-beta). Poor ROI vs the goal.
- **NOW SPIKING (user chose):** REAL WebGPU on web via emscripten emdawnwebgpu port + wgpu's webgpu (not gles) backend on wasm32-emscripten — the only path that delivers compute. High uncertainty; this fork deliberately didn't build it. Verdict pending.
Live pipeline UNTOUCHED throughout (scratch /tmp/webgpu-spike, image webgpu-rustwasm). Non-threaded WebGL2-backed test export at /tmp/webgpu-spike/minimal-export (104MB, no COOP/COEP) available as a fallback data point. See [[voxiverse-webgpu-fork-spike]].
