2026-07-23 throwaway spike: can VOXIVERSE migrate Godot 4.4.1→David Walter's WebGPU fork keeping godot_voxel? VERDICT **YELLOW** (module compat GREEN; overall gated by the WebGPU Rust-lib build).

**Make-or-break = GREEN, proven natively.** godot_voxel **v1.6** (commit 595f52ee) compiled all 330 C++ files + LINKED + registered all 70 Voxel* classes (incl. VoxelTerrain/VoxelTool/VoxelBuffer/VoxelMesherBlocky/VoxelGeneratorScript/VoxelViewer — every class our 64 GDScript files use) against the fork's Godot **4.6.3-rc** tree. Native linuxbsd editor, webgpu=no, built in 8.5 min in our existing `voxiverse/godot-build:4.4` image (scons 4.0.1/gcc11 suffice). Corroborated: Zylann ships an official "Godot 4.6.stable + Voxel Tools 1.6" build. Map: godot_voxel v1.6→4.6, v1.4.1(ours)→4.4.1.

**Fork:** github.com/davnotdev/godot, branch `4.6-webgpu-rebased` (MIT, public — no gated blocker), base = Godot 4.6.3-rc, HEAD 2026-04-29, commit msg "continuing rebasing" (in-progress, single maintainer). Other branches: `webgpu`, `webgpu-firefox`, `4.5-*-webgpu`.

**Biggest blocker (why not GREEN):** the WebGPU renderer (drivers/webgpu/SCsub) links prebuilt Rust static libs `wgpu_native`+`naga_native`+`spirv_webgpu_transform` from davnotdev's OWN crate forks, pinned by commit in thirdparty/*/TAG, NONE vendored, NO in-repo build script. Building the WebGPU web template means first building those Rust forks to wasm32 static libs — undocumented, unproven. Also: emsdk must jump **3.1.64→4.0.11** (Godot 4.6 hard-requires ≥4.0.0; fork+stock 4.6 CI both pin 4.0.11). Also: our project is renderer-LOCKED to gl_compatibility; WebGPU's value is Forward+/Mobile → renderer + shader port (our ATMO2 shaders are gl_compat-specific). Also: need WebGL2 fallback for non-WebGPU browsers.

**WEB-side spike (2026-07-23, follow-up) = YELLOW (feasible, de-risked).** The feared blocker (build the 3 WebGPU Rust libs to wasm) is SOLVED. Recipe in image webgpu-rustwasm (Rust 1.91 + emsdk 4.0.11 + wasm32-unknown-emscripten): clone davnotdev forks wgpu-native@4134c87 (+webgpu-headers submodule 7d3186c), naga-native, spirv-webgpu-transform at TAG commits; set BINDGEN_EXTRA_CLANG_ARGS to emscripten sysroot; add wgpu-core feature `fragile-send-sync-non-atomic-wasm` (fixes the `send_sync`/ContextError Send E0277); crate-type staticlib-only + `--no-default-features --features wgsl,spirv,glsl` (drop native gles/EGL/dx12/metal/vulkan backends). Produced libwgpu_native.a 26MB / libnaga_native.a / libspirv_webgpu_transform_ffi.a. These LINK into the Godot web wasm: `scons platform=web target=template_release webgpu=yes threads=no` produced a 107MB .wasm with **0 undefined symbols**. Two last-mile issues, both understood: (1) fork's WebGPU RD driver has a 64-bit-only `static_assert(sizeof(WGPUMultisampleState)==24)` that fails on wasm32 (16B) — present unguarded on BOTH 4.6-rebased AND primary `webgpu` (now Godot 4.7.0-beta) branches → web path is NOT turnkey, needs source patch (canary for more 32-bit assumptions); (2) exceptions-mode: Rust libs (unwind) vs Godot `-fno-exceptions` → rebuild libs panic=abort (naga/spirv clean; wgpu-native hit a -Zbuild-std Cargo.lock quirk). NOT yet done: threaded build (threads=yes, needed by godot_voxel) needs libs rebuilt WITH wasm atomics via custom target JSON (RUSTFLAGS +atomics does NOT reach the cfg build-script — proven); in-browser RUNTIME unverified (headless can't test WebGPU render). Effort to a working WebGPU web build of our project: ~2-4wk + gl_compat→Forward+ shader port; gated on David publishing a web recipe or us upstreaming wasm32 driver fixes.

**Runtime de-risk (2026-07-23) — RUNNABLE web export PRODUCED + a big architectural catch.** Clean emit achieved: fix the exceptions blocker by building all 3 libs `panic=abort` (the wgpu-native holdout was a `rust-toolchain.toml`-pinned `1.91` toolchain lacking rust-src/`library/Cargo.lock` → force `RUSTUP_TOOLCHAIN=1.91.1`); with no exception code in the libs Godot's default `-fno-exceptions` links clean (the alt "match Godot to unwind" via `-fexceptions` FAILS: emscripten `-wasm-enable-sjlj` conflicts with `-enable-emscripten-cxx-exceptions`). Patched the one 64-bit `static_assert(sizeof(WGPUMultisampleState)==24)`. Built full web template (`.zip` 29MB, `.wasm` 107MB, `.js` 464KB), installed as `web_nothreads_release.zip` under export_templates/4.6.3.rc/, exported a minimal Forward+ scene → complete set in /tmp/webgpu-spike/minimal-export (index.html/js/wasm(107MB)/pck, 104MB total). threads=no ⇒ NO COOP/COEP needed to serve. CRITICAL CATCH: on the emscripten target this fork's wgpu-hal has NO webgpu backend — `Emscripten: {all(target_os="emscripten", gles)}`, vulkan is native-only — so "Godot WebGPU" on web is **wgpu-on-WebGL2**, NOT browser `navigator.gpu`. It REQUIRES the `gles` cargo feature (I first dropped it → backend-less export with no device; rebuilt with `--features wgsl,spirv,glsl,gles`, Godot's emscripten GL resolved the `eglGetPlatformDisplay` symbols, wasm now has WebGL glue). Implication: this path does NOT deliver the WebGPU value prop (compute shaders / navigator.gpu) on web — that would need the emscripten emdawnwebgpu port + a real webgpu-on-emscripten backend this branch lacks. In-browser draw still unverified (GL-context sharing Godot↔wgpu-gles is the risk). SCsub gotcha: `env.Depends(driver_obj, thirdparty_obj=[])` so scons does NOT track the .a — must `rm` bin/*.wasm to force a relink after swapping libs.

**REAL WebGPU + compute on web (2026-07-23 final spike) = RED, well-evidenced.** Three layers: (1) emscripten **emdawnwebgpu port** (Dawn v20250531 → navigator.gpu) is GREEN — a minimal C `wgpuCreateInstance` program compiles+links+references navigator.gpu/RequestAdapter in emsdk 4.0.11 (90KB wasm; emscripten's own bundled C++ test is API-skewed but the port works). (2) **wgpu webgpu-backend-on-emscripten** = RED — wgpu's webgpu backend is web-sys (wasm32-unknown-**unknown** only), explicitly disabled on emscripten; davnotdev's wgpu-hal has NO webgpu module (dx12/gles/metal/noop/vulkan). So wgpu-native on emscripten is PERMANENTLY WebGL2 — never navigator.gpu. (3) **Godot's WebGPU RD driver on emdawnwebgpu** (the only real path) = RED for reasonable effort: the 6572-line driver is architected on wgpu-native-EXCLUSIVE features Dawn/browser-WebGPU lacks — SPIR-V shader passthrough (`WGPUShaderSourceSPIRV`/`SpirvShaderPassthrough`; Dawn accepts ONLY WGSL, Godot emits SPIR-V), push constants via "Immediates" (`wgpuComputePassEncoderSetImmediates`, `WGPUPipelineLayoutExtras`; no push constants in std WebGPU), `WGPUNativeTextureFormat`×33, `WGPUBindGroupEntryExtras`×12, `WGPUInstanceExtras`, `wgpuDevicePoll`. Porting to Dawn = re-architect shader pipeline (SPIR-V→WGSL runtime translation) + push-constant→UBO emulation + format/event/poll rework = multi-month engine-level effort duplicating Godot's OFFICIAL WebGPU proposal (#4806). CONCLUSION: David's fork deliberately uses wgpu-native (gives Godot's RD SPIR-V + push constants + all formats) and accepts WebGL2-only on web as the price. **The strategic goal — compute-baked high-res terrain on web — is NOT deliverable via this fork at any reasonable cost. Real WebGPU+compute on web will come from Godot's official renderer (no timeline), not this community fork.** Definitive RED on the whole WebGPU-migration-for-compute thesis.

Recommendation: do NOT migrate the LIVE pipeline now (violates the "web demo must load & be playable" non-negotiable given fork maturity + unproven wasm lib chain); module-compat being green means revisit when the fork stabilizes.
