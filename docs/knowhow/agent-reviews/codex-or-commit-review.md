## The gate's BLIND SPOT (attack here hardest)
The headless dummy rasterizer's region-updates are NO-OPS, so G-OR-PART-EQ validates the CPU byte-MIRROR pack, NOT the actual GPU region APPLICATION. So the real risk — a wrong offset/stride/size in the mesh_surface_update_*_region calls, or a wrong buffer layout assumption — is UNTESTED by the gates. Scrutinize the region math:
1. VERTEX region: the vertex buffer is claimed pos-only 12B/vert (no normals under WS3). The update writes `_arena_vbytes` slice for a slot at `vert_base*12`. Verify: (a) offset = slot*VERTS_PER_TILE*12 exactly; (b) size = VERTS_PER_TILE*12; (c) the buffer is REALLY pos-only (does add_surface_from_arrays with these arrays + flags=0 produce a 12B vertex stride, or does Godot pad/interleave? confirm against the pinned 4.4.1 source in docker/engine/cache/godot). A wrong stride = every vertex shifted = garbage terrain.
2. ATTRIBUTE region: claimed RGBA8 color(4) + f32 uv(8) + f32 uv2(8) = 20B, offsets 0/4/12. Verify the ATTRIBUTE buffer layout Godot actually produces (order, packing, alignment) matches. Is color at offset 0 or after something? Is uv2 present (the arrays include ARRAY_TEX_UV2)? Does Godot interleave attributes in a different order than color→uv→uv2?
3. COLOR QUANT: `int(clampf(c*255.0,0,255))` — is this Godot's EXACT u8 conversion? Godot may ROUND (round(c*255)) or use Math::fast_ftoi, not truncate. If it truncates and Godot rounds, off-by-one on every color. The boot self-check (_or_pack_self_check) is claimed to catch this — VERIFY the self-check actually byte-compares against a real mesh_get_surface readback and covers the rounding-boundary (e.g. 0.5*255=127.5). If the self-check is wrong/weak, corruption ships.
